  ◆ A. GPU 侧 per-quad 深度排序
    做法: 在现有 culling 管线里加排序：1) 扩展 entity/pass-through culling shader，用已上传的 viewMatrix 算 quad 质心视图空间深度 key（同时可写进现有 VaryingData 或独立 key buffer）；2) 新增 3-4 个 compute：256 桶直方图 → 前缀和 → scatter（radix），索引缓冲 ping-pong；3) 在 AcceleratedBufferSource.prepareBuffers 内仅对 TRANSLUCENT 桶追加这些 dispatch + SSBO barrier；4) 必须切换到 DrawMethodType.INDIRECT，因为 BASEVERTEX 的索引是共享规范前缀、无法按 quad 重排。
    可行性: 中。所需数据（顶点 SSBO、viewMatrix uniform、atomic counter、PolygonsOut 索引 scatter）与整套 dispatch/override 基础设施已存在，见 features/culling/OrientationCullingProgramDispatcher.java:41 与 shaders/core/culling/entity_quad_culling_shader.compute。但需新写 4 个 compute shader、新增 key/index ping-pong 缓冲、并把 BASEVERTEX 换成 INDIRECT（当前配置正是 BASEVERTEX，FeatureConfig.java:159）。
    风险: 高。① 放弃 BASEVERTEX 的跨帧索引缓存优化（说明书明说 INDIRECT 在 draw call 多时更慢）；② 每帧为每个 translucent builder 额外 4-12 次 dispatch，对「1100 只羊」这类几何量大的场景可能吃掉收益；③ 排序只能局限在单个 builder 的连续顶点范围内，跨 builder 无法统一排序；④ 需要真正的全局 radix/bitonic 实现（单 workgroup 只够 ~1-2k quad，而一个 layer+RenderType 桶含全部实体的 quad）。
  ◆ B. 半透明几何不写深度
    做法: 必须绕过 GlCommandEncoder.applyPipelineState（它会按 pipeline 重写 _depthMask）。两条可行实现：(i) mixin GlCommandEncoder.applyPipelineState（或 mixinextras @ModifyExpressionValue 作用于 DepthStencilState.writeDepth() 调用点），对 sortOnUpload 的 RenderType 强制返回 false；(ii) 用 RenderPipeline.builder() 克隆一份 writeDepth=false 的 ENTITY_TRANSLUCENT（Builder 全 public），配 RenderSetup.builder(cloned).withTexture(...).useLightmap().useOverlay().affectsCrumbling().sortOnUpload() 建新 RenderType，需先用 AW 打开 RenderType.create。在 pass 内直接调 GlStateManager._depthMask(false) 不可靠。
    可行性: 中。API 上可行（Builder 全 public，AW 条目可加），但无法局部生效——深度状态由 pipeline 决定且被 encoder 重写，必须动 26.1 的状态机。
    风险: 中高。① 与 vanilla 语义不一致：vanilla 靠 per-quad 排序 + 写深度保证正确，去掉写深度后「后画的近处几何」不再自动胜出，多实体重叠的半透明混合仍会错，只是从「硬遮挡」变成「顺序混合」；② 对单模型自重叠（史莱姆外壳）恰好有效；③ 但本症状中的「内部显示为不透明」「眼睛全黑」与深度无关，B 未必能修好全部现象；④ 需要在 encoder 层做全局改动，影响所有走该 RenderType 的绘制（含 Iris 路径）。
  ◆ C. 保证提交顺序 = 排序后的顺序（CPU 侧排序）
    做法: C'（per-entity，低成本）：给 IDrawContext 增加一个「相机距离」次级排序键并扩展 compareTo，配合 SortedLayerStorage（或给 SeparatedLayerStorage 的 TRANSLUCENT 桶换成 SortedLayerContexts），让同 (layer,RenderType) 内的 drawContext 按距离绘制。C（per-quad，高成本）：在提交阶段就按距离写 quad —— 需放弃共享 mesh + sharing 矩阵架构，改为每个 quad 独立实例，且 BASEVERTEX 索引无法重排、INDIRECT 索引由 GPU 生成，等价于重写整个上传/绘制链路。
    可行性: C' 高（排序框架已存在，改动集中在 compareTo 与层级语义）；C(per-quad) 极低——CPU 在提交时拿不到变换后的顶点位置，且顶点按提交序写入 ring buffer，无法事后重排。
    风险: C' 中：layer 目前承载「盔甲/纹饰/渲染层顺序」（FeatureRenderDispatcherMixin 把 order 桶映射为 layer），把深度塞进同一个键会破坏该层级顺序，必须引入独立次级键（SortedLayerContexts + 稳定排序）。C 的 per-quad 会摧毁 mesh 合并与 dense upload（当前性能收益的来源）。
  ◆ D. 只加速「不需要排序」的半透明类型（白名单）
    做法: 保持 supportTranslucent=false 不动，在 AcceleratedBufferSources.getBuffer 的门控里加一个「按 RenderType 白名单放行」集合，只收几何天然无自重叠或单/少数 quad 的类型（候选：entity_translucent_emissive、end_crystal_beam、beacon_beam、entity_shadow）。可按 RenderType 实例或 name() 做 Set 判定。
    可行性: 高。改动最小（无新 shader、无状态机改动），只影响 AcceleratedBufferSources.java:39-50 的条件。
    风险: 低，但对本次症状零帮助：白名单里没有 entity_translucent（史莱姆外壳、玩家、盔甲架、经验球都在这一类），效果等价于方案 E。且「是否需要排序」无法从 RenderType 自动推导（取决于 mesh 是否凸/是否自重叠），白名单必须人工维护，判定标准脆弱（同类型不同模型可能一个凸一个不凸）。
  ◆ E. 保持 DISABLED（现状，默认值已是 DISABLED）
    做法: 不写代码。force_translucent_acceleration 默认 DISABLED 时，AcceleratedBufferSources.getBuffer 对 isTranslucent 的 RenderType 返回 null → 该几何回落到 vanilla MultiBufferSource，走 vanilla 的 per-entity + per-quad 排序。
    可行性: 高（零成本，HEAD=4e8a7c9 已是此状态；上游 reFabricated 同样从不启用 supportTranslucent）。
    风险: 低。代价可精确枚举：仅 entity 格式下 3 个 sortOnUpload 类型不加速——entity_translucent（史莱姆外壳、玩家、盔甲架、经验球、马纹、潜影贝子弹、头颅）、entity_translucent_emissive（监守者）、entity_translucent_cull_item_target（LivingEntityRenderer 的 item-target 模式）。此外 item_translucent/armor 透明件等也回落。主力负载（羊/牛等的 entity_cutout，方块/方块实体的 BLOCK 格式）完全不受影响。
  ◆ F. 无光影加速 / 有光影回退（第三态）
    做法: 在 getBuffer 门控里追加 `IrisApi.getInstance().isShaderPackInUse() == false` 条件（compat/iris 已有 IrisApi 使用先例）。
    可行性: 高（两三行改动）。
    风险: 对本症状无价值：用户实测「关光影 + force ENABLED」症状完全相同，说明半透明加速的失败与 gbuffer/MRT 无关，F 只是把同一 bug 藏在无光影时才暴露的位置。F 只对「Iris 专属」的那条问题线（memory/iris-shader-entity-invisible.md 的绘制时机/MRT）有意义，那是另一个问题。
